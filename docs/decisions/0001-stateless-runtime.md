# ADR-0001：采用无数据库运行时

- 状态：Accepted
- 日期：2026-07-21

## 背景

MVP 是一个公开的个人作品集项目，预计早期并发不超过 10。报告完全由 Steam 当前公开数据生成，不需要用户编辑内容，也不需要跨设备保存历史报告。

引入数据库会带来数据保留政策、迁移、账号关联、隐私说明和运维成本，但不会改善当前核心体验。

## 决策

MVP 不使用数据库。

- 玩家报告仅存在于单次服务端请求、React 内存和当前标签页的 `sessionStorage` 中。
- Steam OpenID 只用于确认 SteamID，不创建站内账户。
- OpenID 临时状态使用短时效、随机且 HttpOnly 的 Cookie；验证后的 SteamID 只存在于一次性两分钟 Cookie。
- 海报生成时重新读取或重新验证数据，不从数据库取报告。
- 玩家相关 API 响应使用私有且不缓存的策略。
- 日志不保存完整 SteamID、昵称或游戏列表。

## 结果

优点：

- 架构简单，部署和开源成本低。
- 没有玩家数据泄漏后的长期存量风险。
- SteamID 输入与 Steam 登录可以复用同一条生成管线。
- 分析引擎保持无状态，易于测试。

代价：

- 刷新或关闭标签页后可能需要重新请求 Steam。
- 无法提供历史报告、永久分享链接或跨设备恢复。
- 海报生成可能再次触发 Steam 请求。
- 服务端无状态限流需要依赖部署平台能力。

## 未来重新评估条件

只有出现以下需求时才重新讨论数据库：

- 用户明确需要保存历史报告。
- 需要永久分享某一份报告。
- Steam 请求量大到必须建立玩家级快照缓存。
- 需要账号偏好、收藏或跨设备同步。

即使未来加入数据库，也应默认最小化保存，并把静态游戏元数据与玩家数据分开。

## 未选择的方案

### 从一开始使用关系型数据库

拒绝原因：当前没有持久化业务需求，增加了不必要的隐私和部署负担。

### 在分享 URL 中序列化完整报告

拒绝原因：URL 过长、容易泄漏玩家数据、不可控且难以撤销。

### 使用二维码携带 SteamID

拒绝原因：产品已决定二维码只负责引流首页，而不是重现原玩家报告。
